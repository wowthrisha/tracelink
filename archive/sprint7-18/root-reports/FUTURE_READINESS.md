# Future Feature Readiness — Sprint V7.0 (Phase 3)

Honest, evidence-based readiness assessment for 12 future capabilities (mobile and desktop clients split, as they have materially different requirements). Verdicts are not inflated — most areas are correctly PARTIALLY READY or NOT READY for a codebase at this stage, and that's an accurate reflection of maturity, not a criticism.

| Capability | Verdict | Evidence | What would be needed |
|---|---|---|---|
| **AI analytics** | PARTIALLY READY | `models/reading_analytics.py` already stores `engagement_score`/`absorption_score`/`focus_score`/`reading_consistency`/`attention_stability`/`understanding_confidence` per session, and `document_complexity` — but every one is a hand-written deterministic formula (`reading_analytics_service.py`), not a model output. `AccessEvent.metadata_json` gives a flexible payload slot for future signals. | The score columns and aggregation service are a ready-made slot to swap formula output for model output, but there is zero inference infrastructure (no model-serving, no batch pipeline, no feature store) — that's new build, not a retrofit. |
| **LMS integrations** | NOT READY | `WEBHOOK_EVENTS` is a fixed 3-value set with no course/roster/assignment concepts; `ShareLink` has no LTI/course/section/due-date fields. | New data model (course/roster mapping), an LTI 1.3 or vendor-specific auth flow, new webhook event types, and grade-passback logic — essentially new build on top of existing generic webhook plumbing. |
| **Mobile clients** | PARTIALLY READY | `frontend/api.js` is largely a reusable thin fetch wrapper, but `auth()` talks directly to Supabase via `<meta>` tags injected into the HTML page rather than a documented backend contract, and download/URL helpers bake in DOM assumptions (`document.createElement('a')`, blob URLs). | Extract the Supabase auth flow into a documented mobile-friendly contract; replace DOM-dependent helpers with a plain data API. |
| **Desktop clients** | PARTIALLY READY | API-key auth with scopes works headlessly today — a legitimate non-browser credential path already exists. But there's no OAuth device-code/PKCE flow; the only interactive auth is a password-grant form. | Add a device/PKCE OAuth flow, or formalize API-key-based desktop login as the supported path. |
| **API versioning** | NOT READY | Every router declares an unversioned prefix (`/api/documents`, `/api/orgs`, etc., confirmed across all 16 routers); no `/v1/` or header-based scheme anywhere. | Introducing versioning means either prefixing every router and rewriting every hardcoded URL in `frontend/api.js`, or adding a header-based scheme — a non-trivial retrofit either way, since nothing was designed with a version-indirection layer. |
| **Multi-tenancy** | PARTIALLY READY | Organizations/OrgMembership exist with a role hierarchy, and `documents.py`/`links.py`/`storage.py`/`admin.py` do filter by `org_id`. But `Document.org_id` is optional, and `webhooks.py`/`api_keys.py`/`billing.py`/`notifications.py`/`groups.py`/`annotations.py`/`reading.py`/`viewer.py` are **not** org-scoped at all — scoped to `user_id` only. | Tenant isolation is enforced only for document/link/storage resources today; billing, webhooks, API keys, and groups would each need an `org_id` column and migration before being considered truly org-scoped. |
| **Organization scaling** | NOT READY | `list_members` runs unbounded with no pagination, and fires a parallel outbound HTTP call to Supabase's admin API per member on every page load (`asyncio.gather` over all members — scales linearly with org size). No settings/config JSON column exists on `Organization` at all. | Pagination on member listing, batching/caching the Supabase email lookups, and a flexible settings column before per-org configuration can grow without a migration every time. |
| **Billing expansion** | NOT READY | `UserBilling` is keyed by `user_id` (not `org_id`) — billing is strictly per-user. Plans are two hardcoded string constants (`PLAN_FREE`/`PLAN_PRO`) with no usage-metering fields at all. | Moving to per-org billing requires re-keying the billing table (or adding a parallel org-billing table); usage-based/multi-tier billing requires new metering columns/tables — schema changes, not config changes. |
| **RBAC expansion** | NOT READY | `ORG_ROLES` is a fixed 4-value Python tuple, and `role_gte()` is a positional-index hierarchy check, not a permission-bitmask or capability system. No join table exists for granular/custom permissions. | Replacing the fixed ladder with a permissions table (role → capability mapping) or per-membership capability overrides — every `role_gte(role, "admin")`-style check throughout `orgs.py` currently assumes exactly 4 fixed rungs. |
| **Internationalization** | NOT READY | No i18n library or translation-function abstraction exists anywhere (confirmed via grep — no `i18n`/`react-intl`/`useTranslation`). All 13 screens hardcode English strings directly inline in JSX. | Introduce an i18n library and a strings-extraction pass across all 13 screens — every hardcoded string literal would need to become a translation-key lookup, a full-repo mechanical refactor. |
| **White-label deployments** | NOT READY | `tokens.js` hardcodes a single brand palette with no theme-switching mechanism; "SecureDoc" appears hardcoded inline across all 13 screens (91 occurrences). The only per-org branding-adjacent field, `Organization.custom_domain`, solves the URL but carries no logo/color/name override. | Extract a theme/branding config object referenced everywhere the palette/product-name is currently hardcoded, plus a per-org branding table. |
| **Enterprise SSO (SAML/OIDC)** | NOT READY — confirmed inert placeholder | `Organization.saml_domain` exists as a plain nullable column, fully CRUD-able via the orgs API — but a repo-wide grep finds **zero** other SAML references: no library, no IdP metadata handling, no ACS endpoint, and `auth.py`'s `get_current_user` never reads `saml_domain`. | This requires a SAML/OIDC library, an assertion-consumer-service route, IdP metadata exchange, and wiring `saml_domain` into the actual auth-resolution path — none of which exists today despite the schema field suggesting otherwise. |

## Net assessment

Of 12 capabilities assessed: **0 fully READY**, **4 PARTIALLY READY** (AI analytics, mobile, desktop, multi-tenancy), **8 NOT READY** (LMS, API versioning, org scaling, billing expansion, RBAC expansion, i18n, white-label, SSO). This is a realistic profile for a product that has grown organically through feature sprints rather than been built against a future-proofing roadmap — the good news is that the two structural properties that would make all of these *harder* to retrofit (a leaky layering, or inconsistent tenant scoping baked in everywhere) are largely absent: the backend's service layering is clean (see `LONG_TERM_MAINTAINABILITY.md`), and the Organizations model, while not universally applied, is a genuine, working tenancy primitive to extend rather than replace. The single highest-leverage prerequisite before tackling any of the "NOT READY" items that touch auth or tenancy (SSO, RBAC expansion, multi-tenancy completion) is finishing the `org_id` scoping gap on `webhooks.py`/`api_keys.py`/`billing.py`/`groups.py` — every one of those future features gets meaningfully harder if that gap isn't closed first.
