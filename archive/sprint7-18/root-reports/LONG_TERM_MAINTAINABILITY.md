# Long-Term Maintainability — Sprint V7.0 (Phase 1)

Framing: would this codebase, as it stands, be comfortable for 20 engineers to work in concurrently over 5 years of continuous feature growth? Reviewed module by module: would another engineer immediately understand it, can it evolve without breaking siblings, is responsibility/ownership/naming obvious. This is an assessment document — per this sprint's own instruction, no bug fixes were made; findings from V6.0's implementation work are cited where they establish a baseline.

## Backend modules

| Module | Would a new engineer understand it immediately? | Can it evolve independently? | Responsibility obvious? | Verdict |
|---|---|---|---|---|
| `routers/` (16 files) | Yes, with one caveat — DI pattern (`Depends(get_db)`/`Depends(get_current_user)`) is near-universal and instantly recognizable once you've seen one router. The caveat: `annotations.py` and `storage.py` don't use `APIRouter(prefix=...)` like the other 14 files, hardcoding full paths instead — a newcomer copying the "add a router" pattern from one of these two would learn the wrong convention. | Mostly — routers are thin in 11/16 files. `documents.py:upload_document` (~180 lines) and `viewer.py:download_document`/`get_page` are the exceptions: business logic embedded in the handler means changing upload quota rules or download watermarking risks touching request-parsing code in the same diff. | Yes for 14/16 files (one router = one resource family). `annotations.py` straddles two resource families (`/api/viewer/annotations/*` and `/api/documents/*/annotations`, `*/feedback`) in one file — a new engineer looking for "where do I add a new document-owner annotation feature" has to already know it's not where the URL prefix would suggest. | **Mostly maintainable**, two real friction points (prefix convention, `annotations.py` scope). |
| `services/` (~20 files) | Yes — names are descriptive (`link_service.py`, `webhook_service.py`, `retention.py`) and the layering (routers call services, services never call routers) is clean and verified with zero violations. | Yes, generally — this is the strongest-scoring dimension in the whole review. One exception: `reading_analytics_service.py:ingest_batch` (~220 lines, the largest function in the repo) mixes validation/session-upsert/aggregation/complexity-update in one function, so a change to any one concern risks touching the others in the same diff. | Yes — service file names map 1:1 to their domain concept, no ambiguity found. | **Strong.** |
| `models/` (files under `models/`) | Yes — SQLAlchemy models are conventional and consistently structured. One real gap: `Document.org_id` has no `ForeignKey` constraint (unlike `group_id`/`parent_document_id` on the same model) — a new engineer adding org-delete logic would reasonably assume referential integrity is enforced at the DB level here and be wrong. | Mostly — `ORG_ROLES` is a fixed 4-value tuple with no extension point (see `FUTURE_READINESS.md` for the RBAC-expansion implication); adding a 5th role means touching every `role_gte()` call site's assumptions, not just the tuple. | Yes. | **Strong, with the one FK gap as a real trap for the next engineer.** |
| `schemas/` (Pydantic request/response models) | Partially — only 3 of 16 routers (`documents.py`, `links.py`, `groups.py`) actually use them; the rest validate via raw `body: dict` with manual `.get()` extraction (`orgs.py` alone has 5 untyped write endpoints). A new engineer reading `documents.py` would reasonably conclude "this project uses typed schemas" and then be surprised when `orgs.py`/`webhooks.py`/`api_keys.py` don't. | The untyped routers are harder to evolve safely — adding a field to `orgs.py`'s create-org request means updating a `.get()` call and hoping every caller matches, with no compiler/Pydantic help catching a typo. | The distinction between "why does this router use schemas and that one doesn't" is not documented or evident from the code — looks historical/accidental rather than a deliberate boundary. | **Weakest backend dimension.** This is the single highest-leverage "would 20 engineers be confused" finding in the backend. |
| `workers/` (Celery tasks) | Yes, once you understand `celery_app.py`'s `include=` mechanism — which V6.0's work demonstrated is exactly the kind of thing that silently breaks without anyone noticing (the webhook-task-registration bug). This is a real "hidden coupling" risk: a new engineer adding a new task module has no automated check reminding them to add it to `include=`. | Yes, task-by-task, once registered. | Yes — one file per task family (`tasks.py`, `cleanup.py`, `webhook_tasks.py`). | **Good, but with a proven sharp edge** — recommend a regression-test convention (like the one added in V6.0) for every new task module going forward, not just webhook_tasks retroactively. |
| `middleware/` | Yes — small, single-purpose files (`https_redirect.py`, `json_logging.py`, `metrics.py`, `request_id.py`, `security_headers.py`, `trusted_proxy.py`), each doing exactly what its name says. | Yes. | Yes. | **Strong — this is the most obviously well-factored directory in the backend.** |
| `utils/` | Yes — `crypto.py`, `ssrf_guard.py` are small and focused. | Yes. | Yes. | **Strong.** |

## Frontend modules

| Module | Would a new engineer understand it immediately? | Can it evolve independently? | Responsibility obvious? | Verdict |
|---|---|---|---|---|
| `screens/` (12 files) | Mostly yes — one screen per nav item is intuitive. `AccessScreen.jsx` (~900 lines, 53 `useState` calls, 3 unrelated feature domains sharing only `docId`) is the clear outlier — a new engineer asked to "add a feedback-export option" would have to navigate a 900-line file to find the ~300 lines that are actually relevant. | Everywhere except `AccessScreen.jsx` — its 3 domains (links/feedback/annotations) can't be touched independently today even though they're logically separable; a natural 3-way split (`LinksTab`/`FeedbackTab`/`AnnotationsTab`) was already identified in V6.0's work but not implemented (out of scope for a "no new refactors" sprint). | Yes, one screen = one nav item, with the AccessScreen exception noted. | **Good, with one clear, already-diagnosed exception.** |
| `components/` | Yes — atoms (`atoms.jsx`) vs. feature-scoped subfolders (`upload/`, `access/`, `analytics/`) is a sensible, discoverable split. One friction point: 7 "reusable" components (`PageThumb.jsx`, `TocSidebar.jsx`, `SearchPanel.jsx`, `DocumentPicker.jsx`, `ViewerInfoPanel.jsx`, `QuickShareModal.jsx`, `AccessLog.jsx`) call `window.SecureDocAPI` directly instead of receiving data via props — a new engineer reusing one of these elsewhere would unexpectedly get a network dependency they didn't ask for. | Mostly, with the above caveat — those 7 components can't be reused in a context that doesn't want their embedded fetch behavior without a refactor. | Yes for the atoms/tokens split; the 7 secretly-networked components blur the "presentational vs. container" line that the rest of the codebase mostly respects. | **Good, one systemic pattern gap (already diagnosed in V6.0, not yet fixed).** |
| `hooks/` (8 files) | Yes — each hook does one clearly-named thing, no hook imports from `screens/` (verified, zero violations), so the dependency direction is always "screen depends on hook," never the reverse. | Yes. | Yes. | **Strong.** |
| `constants/tokens.js` | Yes for color — a full, well-organized color-token system exists. **No** for spacing — there is no spacing scale at all (confirmed this sprint: 44 distinct padding value-pairs and 13 distinct gap values across 12 screens with no tier system), so a new engineer has no way to know if `padding: '14px 16px'` vs `'14px 18px'` on two visually-identical containers is intentional or accidental drift. | The color system evolves fine; the absent spacing system means every new screen re-invents spacing values from scratch rather than reusing a scale. | Yes for what exists; the gap (no spacing tokens) is itself the finding. | **Half-strong** — color tokens are a model to follow, spacing tokens are the most concrete "add this and stop future drift" recommendation in the whole frontend review. |
| `utils/` (`viewer.js`, `feedback.js`) | Yes, small and focused. | Yes. | Yes. | **Strong.** |
| `api.js` (single 1070-line API client) | Yes at the level of "one file, one job" (talk to the backend) — genuinely easy to find any given endpoint call. Docked because it's grown to 1070 lines as a flat object literal with no internal grouping beyond comments (`// ── Documents ──`, etc.) — at 5 years/20 engineers' worth of endpoint growth, this file only gets larger with no natural split point designed in. | Yes today; the flat structure means every future endpoint addition is one more entry in an ever-growing single file rather than a new module. | Yes — unambiguous, single responsibility. | **Fine today, a known future scaling concern for the file itself (not the pattern it embodies).** |

## Cross-cutting maintainability observations

- **Ownership is not documented anywhere** — no `CODEOWNERS` file exists (confirmed this sprint). For a 20-engineer organization, "who do I ask about the webhook delivery pipeline" has no answer in the repo itself today.
- **The backend/services layering is the strongest asset in this codebase** for 5-year maintainability — zero cross-layer violations, verified twice now (V6.0 and this sprint), across models/services/routers. This is the one structural property most worth protecting as the team scales.
- **The single most consequential maintainability gap found this sprint**: the untyped-vs-typed Pydantic schema split (`orgs.py`/`webhooks.py`/`api_keys.py` vs. `documents.py`/`links.py`/`groups.py`) is invisible until you've read both kinds of router, and nothing in the codebase explains why it exists — this is exactly the kind of inconsistency that compounds as more engineers copy whichever pattern they encountered first.

Full evidence trails for every claim above are in `MODULE_BOUNDARIES_AND_CODE_QUALITY.md` (V6.0) and the code-standardization findings this sprint (see the accompanying standardization document).
