# Before / After Index

## WATERMARK-001 — Visible watermark was a near-total no-op on all shared-link pages

- **Before**: `Before_After/WATERMARK_BUG_before_8x_contrast_no_watermark_visible.png` — live production page fetched via a real anonymous, password-verified share-link session, contrast-enhanced 8x. No watermark pattern visible anywhere despite the link being configured Watermark: On.
- **After**: `Before_After/WATERMARK_BUG_after_fix_watermark_correctly_visible.png` — same `WatermarkService.apply_visible_watermark` call (unit-level repro), post-fix. Diagonal tiled watermark renders at the configured 22% opacity as intended.
- **Root cause**: `backend/app/services/watermark.py`, `apply_visible_watermark()` — `overlay.paste(rotated, (rx, ry), rotated)` used the RGBA tile as both the image AND its own paste mask. That blends the alpha value twice (once for pixel color, once for the resulting alpha), squaring it: opacity 0.22 → effective ~0.047 (56/255 → 12/255), invisible after WEBP compression on real page content.
- **Fix**: composite each tile through an intermediate same-size transparent layer with `Image.alpha_composite()` instead of self-masked `paste()`. Confirmed at the unit level (blank-page repro: 0 non-white pixels → 61,018 non-white pixels, darkest pixel 255 → 214) and via the full backend suite (1703 passed, 1 skipped, no regressions).
- **Regression test added**: `backend/tests/unit/test_watermark.py::test_apply_visible_watermark_is_actually_visible` — asserts real pixel-level visibility, closing the gap where prior tests only checked byte-level difference (which the squared-alpha bug still passed).
- **Deploy status**: fixed in the working tree, NOT yet deployed — the live Railway instance (wowmyspace--tracelink.up.railway.app) still serves the pre-fix behavior since nothing has been pushed this session (standing policy: never commit/deploy without explicit request).

## READ-OWNER-001 — Document owner locked out of their own internal Viewer after creating a password-protected share link

- **Repro**: as the authenticated document owner, click a document row from the Upload dashboard to open the internal Viewer. If ANY active share link on that document has a password (or email/domain restriction), the owner's own preview shows the same 'Password Required' gate a public recipient sees — even though the owner is fully authenticated via their own session. Screenshot: `Screenshots/Reading/01_viewer_opened_desktop.png`.
- **Root cause**: `frontend/src/hooks/useViewerSession.js`, the auto-link-resolution effect — when no explicit `publicToken` is given, it fetches all active links for the doc and blindly uses `active[0].token` (whichever link the API happens to return first), regardless of whether that link carries a password/email/domain restriction. A dedicated 'Admin Preview' link (no restrictions) is only auto-created when NO links exist yet — once the owner creates their first restricted share link, that safety net stops being used.
- **Fix**: prefer a link with no viewer-facing restrictions (`!has_password && no allowed_emails && no allowed_domains`), falling back to one labeled 'Admin Preview', and only falling back further to creating a fresh Admin Preview link if neither exists. Verified: frontend suite 13/13 passed, build clean (310.0kb).
- **Deploy status**: fixed in the working tree, NOT yet deployed — reproduced against the live Railway instance before fixing; the live instance still exhibits the bug until this is pushed and deployed.

## BILLING-PLAN-BADGE-001 — Pro users see "FREE" everywhere in the app except the Billing screen itself

- **Repro**: reproduced 3x on fresh page loads against the live Railway instance. A real Pro-plan account (`23z274@psgtech.ac.in`) shows a 'FREE' badge in the persistent sidebar footer on every screen (Upload, Access Control, Storage, Organizations, etc.), while the Billing screen's own 'Current Plan' section correctly shows 'Pro ACTIVE' at the exact same time. Screenshots: `Screenshots/Billing/01_overview_desktop.png` (shows PRO in sidebar, since Billing itself had just loaded) vs. `Screenshots/Storage/01_overview_desktop.png` (shows FREE in sidebar, on a screen that never fetches billing status).
- **Root cause**: `frontend/src/screens/AppShell.jsx` — `const [plan, setPlan] = useState('free')` hardcodes the sidebar's plan state to 'free' on every app load. The ONLY place that ever called `setPlan` was `BillingScreen`'s `onPlanChange` callback, fired after its own `/api/billing/status` fetch — so the badge only ever became correct once the user happened to visit the Billing screen in that session, and reset to the wrong default on every fresh page load.
- **Impact**: cosmetic at minimum (a paying user sees the free-tier badge nearly everywhere), but a real risk if any current or future client-side gating reads this same `plan` state to restrict Pro-only features — that would incorrectly restrict paying users for the entire session.
- **Fix**: added a mount-time `useEffect` in `AppShell.jsx` that fetches `/api/billing/status` directly (same endpoint/pattern `BillingScreen` already uses) as soon as a token exists, setting the real plan before the user ever needs to visit Billing. Verified: frontend suite 13/13 passed, build clean (310.2kb).
- **Deploy status**: fixed in the working tree, NOT yet deployed.
